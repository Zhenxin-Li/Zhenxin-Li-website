Matching Fathers and Sons in PSID with Python and SQL

How income windows change an intergenerational elasticity estimate

Does measuring the same sons’ incomes earlier in adulthood make family income look less persistent across generations? This tutorial uses real Panel Study of Income Dynamics (PSID) records to construct father–son links in Python’s SQLite interface, build comparable income measures, and estimate an intergenerational elasticity (IGE). The comparison keeps the matched father–son pairs fixed while changing income windows.

1. Prepare the records

The inputs are the 2023 Parent Identification File, its matching 1968–2023 Individual File, and nine annual Family Files. Here, “parent income” means total money income of the father’s family; “child income” means the adult son’s own family income. Neither is individual wages.

From this post’s directory, run these commands once to prepare a new database:

python -m pip install -r requirements.txt
python scripts/prepare_psid_linkage.py --raw data/raw --db data/private/psid.sqlite --out data/aggregate
python scripts/psid_analysis.py --raw data/raw --db data/private/psid.sqlite --out data/aggregate --cpi data/aggregate/cpi_annual.csv

If the database is already prepared, skip the first script; it deliberately refuses to overwrite an existing database. Run the Python blocks below in order in one session.

The first script reads official fixed-width column specifications. The second reads family incomes, converts them to 1996 dollars using annual CPI-U, and generates the results below. Original microdata remain local; the README identifies every file and variable.

2. Match people using two-part identifiers

PSID identifies a person by 1968 family ID plus person number. A family ID alone can identify several people. Nor should we require fathers and adult sons to share their current household. This Python block constructs the recorded father links from the loaded tables:

import sqlite3
from pathlib import Path
import numpy as np

con = sqlite3.connect("data/private/psid.sqlite")
con.execute("DROP TABLE IF EXISTS temp.tutorial_pairs")
con.execute("""
CREATE TEMP TABLE tutorial_pairs AS
SELECT r.child_fid, r.child_pnum,
       r.father_fid AS parent_fid, r.father_pnum AS parent_pnum
FROM parent_ids r
JOIN persons c ON c.fid=r.child_fid AND c.pnum=r.child_pnum
JOIN persons p ON p.fid=r.father_fid AND p.pnum=r.father_pnum
WHERE r.father_fid>0 AND r.father_pnum BETWEEN 1 AND 995;
""")
assert con.execute("SELECT COUNT(*) FROM tutorial_pairs").fetchone()[0] == 29218

SELECT retains identifiers. Each JOIN verifies that the child or recorded father exists in the Individual File; WHERE excludes unusable father identifiers. These are recorded father links, not independently verified biological relationships. Uniqueness checks in the preparation script prevent duplicate individual keys.

3. Construct both generations’ incomes

I select sons born in 1955–1959, requiring the father to be a responding household head in 1969–1971 and the son in 1985–1987 and 1995–1997. The father’s interview ages must be 25–65. This gives 197 structurally eligible pairs; usable incomes in all nine observations leave 191 sons and 170 fathers.

Annual family IDs connect each person’s wave record to that year’s Family File. Income refers to the preceding calendar year: the three windows are 1968–1970, 1984–1986, and 1994–1996. I exclude nonpositive, bottom-coded one-dollar, upper-coded, and sentinel values rather than treating them as earnings.

# Family income joins require BOTH the annual family ID and survey year.
income_rows = con.execute("""
SELECT w.fid, w.pnum, w.year, f.real_income
FROM waves w JOIN psid_family_income f
 ON w.family=f.family AND w.year=f.wave
WHERE f.valid=1 AND (
 (w.year BETWEEN 1969 AND 1971 AND w.relation=1) OR
 (w.year IN (1985,1986,1987,1995,1996,1997) AND w.relation=10));
""").fetchall()

# Inspect the aggregation used by the full matching script.
means = con.execute("""
SELECT fid,pnum,window,AVG(real_income) AS mean_income,
 MAX(CASE WHEN year IN (1970,1986,1996)
          THEN real_income END) AS single_income,
 COUNT(*) AS n_valid
FROM psid_income GROUP BY fid,pnum,window HAVING COUNT(*)=3;
""").fetchall()
con.executescript(Path("scripts/psid_match.sql").read_text())
# Inspect the final two-generation join: one row per selected son.
joined = con.execute("""
SELECT k.child_fid,k.child_pnum,
 p.mean_income AS father_mean,e.mean_income AS son_early_mean,
 m.mean_income AS son_mid_mean
FROM psid_candidates k
JOIN psid_measures p
 ON p.fid=k.parent_fid AND p.pnum=k.parent_pnum AND p.window='parent'
JOIN psid_measures e
 ON e.fid=k.child_fid AND e.pnum=k.child_pnum AND e.window='early'
JOIN psid_measures m
 ON m.fid=k.child_fid AND m.pnum=k.child_pnum AND m.window='mid';
""").fetchall()
assert len(joined) == 191

The table flow is parent_ids + persons → verified pairs; waves + family incomes → person-year incomes; person-window summaries + pairs → one row per son. The 29,218 links become 191 complete analysis pairs after the stated restrictions.

GROUP BY makes one row per person and window. AVG averages income levels; MAX retrieves the middle year’s single observation; COUNT requires three valid years. The full SQL then joins the father’s summary and both son summaries to each pair. Aggregating first avoids a three-by-three multiplication of raw income rows.

The nine selected surveys are annual, so each average covers three consecutive income years. I use the middle year of each window for the single-year measure. This compares averaging around the same date, rather than choosing unrelated baseline years.

4. Estimate the IGE on the same pairs

Estimate \(\log Y_i^{son}=\alpha+\beta\log Y_i^{father}+u_i\). A larger \(\beta\) means stronger income persistence: an IGE of 0.5 associates 10% higher parental income with approximately 5% higher son income. Take the log of average real income, not the average of logs.

specs = [("Early single","p_single","c_early_single"),
         ("Midlife single","p_single","c_mid_single"),
         ("Early average","p_mean","c_early_mean"),
         ("Midlife average","p_mean","c_mid_mean")]
for label, px, cy in specs:  # fixed column names, not user input
    rows = con.execute(f"SELECT {px},{cy} FROM psid_matched").fetchall()
    x,y = np.log(np.asarray(rows,dtype=float)).T
    X = np.column_stack([np.ones(len(x)),x])
    beta = np.linalg.lstsq(X,y,rcond=None)[0][1]
    print(f"{label}: n={len(x)}, IGE={beta:.3f}")
con.close()

5. Interpret timing and averaging separately

With the father’s single-year measure unchanged, the son’s later-window estimate is 0.496, versus 0.351 earlier. Sons’ mean interview ages rise from about 29 to 38. This illustrates the sensitivity relevant to life-cycle bias: income early in a career may represent long-run status differently. Calendar conditions and household composition also change, so this comparison alone cannot isolate age effects.

To see the mechanism, suppose early-career log income reflects only half of long-run log-income differences. With accurately measured parental income and unrelated measurement noise, the early-income regression would recover half the long-run IGE. This conditional example explains how age can bias the slope; it is not a fitted description of these PSID records.

Three-year averaging raises the later estimate to 0.525. Temporary fluctuations can partly cancel, making averages a better long-run proxy. But true permanent income is unobserved here. The paired 95% interval for the later-minus-earlier single-year difference is [-0.098, 0.401]; the averaging difference is [-0.069, 0.127]. Both include zero, so neither increase is precisely established.

Takeaway

Link stable person identifiers, aggregate before joining generations, and hold the matched sample fixed. This selected, unweighted sample shows why timing and averaging deserve attention, not a national or causal estimate. Requiring continuous headship and positive income excludes many families; larger estimates are not automatically better estimates.
